## 2. การวิเคราะห์แปลงทำงานอย่างไร

### 2.1 แหล่งข้อมูล
| ข้อมูล | ชุดข้อมูล | ความละเอียด | ช่วงเวลาที่ใช้ |
|---|---|---|---|
| ความเขียว (NDVI), ดินเปลือย (BSI), น้ำผิวดิน (MNDWI) | Sentinel-2 SR Harmonized | 10 m | ค่าเฉลี่ย 365 วัน กรองภาพที่มีเมฆทั้งภาพ < 20% (**ไม่ได้ mask เมฆรายพิกเซล**) |
| "ความชื้นดิน" | Sentinel-1 GRD ค่า VV backscatter (dB) | 10 m | 365 วันสำหรับภาพรวมแปลง, 30 วันสำหรับตารางจุด |
| ระดับพื้นที่ ความลาด ทิศลาด | SRTM GL1 | 30 m | ข้อมูลปี 2000 |
| ฝน | Open-Meteo, WeatherNext (0.25° ≈ 28 km) | — | 7 วัน |

### 2.2 วิธีคำนวณ
- **ภาพรวมแปลง** (`analyze_durian_plot`): เรียก `getInfo()` ต่อกันประมาณ 12–15 ครั้งแบบทีละครั้ง จากโค้ดและคอมเมนต์ใช้เวลา 11–44 วินาที/ครั้ง
- **สถานะความชื้น SWAB** (`_calc_swab`): แปลง VV (dB) เป็น "% น้ำในดิน" ด้วยสูตรเส้นตรงที่ตั้งเอง (−20 dB → 20%, −5 dB → 65%) บวกปรับด้วย MNDWI และระดับพื้นที่
  จากนั้นตัดเป็น 5 ระดับด้วย threshold ที่ตั้งเอง **ไม่เคยสอบเทียบกับการวัดในแปลงจริง** ค่า "น้ำ X% / อากาศ Y%" ที่แสดงจึงดูแม่นกว่าความเป็นจริง
- **ตารางจุดในแปลง** (`get_moisture_grid`): สุ่มจุดทุก 10 m (ไม่เกิน 1,600 จุด) แต่ละจุดจัดสถานะด้วย SWAB
  **สีบนแผนที่เป็นสีเทียบกันเองในแปลง** (contrast stretch) สูตรนี้ถูกเขียนซ้ำไว้ 3 ที่ (Python 2 ที่ + JS 1 ที่)
- **ลูกศรทิศน้ำไหล:** ใช้ทิศลาดของ SRTM เฉพาะจุดที่ลาด ≥ 1.5°
- **วงม่วง "จุดน้ำรวม":** คำนวณฝั่ง JS (`computeFlowGraph`) จุดที่มีลูกศรจากจุดข้าง ๆ ชี้เข้ามาตั้งแต่ 2 ทิศขึ้นไป
- **จุดชื้นสะสม:** จาก `grid_snapshots` รายวัน จุดที่ชื้นอย่างน้อย 60% ของวันที่มีข้อมูล

### 2.3 ใช้กับสวนยกร่องภาคกลางได้หรือไม่ → **ใช้แบบเดิมไม่ได้ ต้องปรับข้อความและซ่อนบางส่วน**
1. **ความสูง/ทิศน้ำ:** SRTM 1 พิกเซลกว้าง 30 m คลุมจุดตาราง 10 m ได้ประมาณ 9 จุด ความคลาดเคลื่อนแนวดิ่งหลายเมตร
   และเป็นข้อมูลปี 2000 ที่วัดผิวบนสุด (รวมทรงพุ่ม) ไม่ใช่ผิวดิน ขณะที่ร่องสวนกว้าง 1.5–2 m และคันดินกว้าง 6–8 m
   จึงเล็กกว่า 1 พิกเซลมาก ในที่ราบภาคกลางความลาดแทบทั้งหมดต่ำกว่า 1.5° → ลูกศรจะแทบไม่ขึ้น
   ส่วนที่ขึ้นมาก็มักเกิดจากสัญญาณรบกวนหรือขอบทรงพุ่ม **ลูกศรและวงม่วงจึงไม่มีความหมายสำหรับสวนยกร่อง**
2. **ร่องน้ำจะถูกอ่านเป็น "น้ำขัง":** พิกเซล 10 m ของ Sentinel ปนกันระหว่างน้ำในร่องกับคันดิน จุดที่ติดร่องจะขึ้นสถานะชื้น/น้ำขังตลอด
   ทั้งที่ร่องน้ำคือน้ำที่ออกแบบให้มีอยู่แล้ว → **มีโอกาสเตือนผิดสูงมาก**
3. **VV ใต้ทรงพุ่ม** ได้รับผลจากใบและกิ่งเป็นหลัก ไม่ใช่ความชื้นดินโดยตรง
4. **สิ่งที่ยังพอใช้ได้:** รูปแบบ "ส่วนไหนของแปลงชื้นกว่าส่วนอื่น" ในช่วงเวลาเดียวกัน และการเปลี่ยนแปลงตามเวลาของแปลงเดียวกัน (เทียบกับค่าปกติของแปลงนั้นเอง)

**แนวทางปรับปรุงที่เสนอให้พิจารณา (ยังไม่ลงมือ):**
- ตัด "น้ำถาวร" ออกก่อนวิเคราะห์ (ใช้ชั้นน้ำผิวดินถาวรเช่น JRC Global Surface Water หรือ MNDWI ที่สูงต่อเนื่องหลายเดือน = ร่องน้ำ)
- เปลี่ยนจาก threshold ค่าสัมบูรณ์ (dB) เป็น "ผิดปกติจากค่าปกติของแปลงนี้เอง" ด้วย Sentinel-1 แบบอนุกรมเวลา
- ข้อมูลความสูงละเอียดกว่า: DEM จาก LiDAR ของหน่วยงานรัฐ (ถ้ามีในราชบุรี) หรือโดรนสำหรับแปลงนำร่อง
- ใช้ผลยืนยันภาคสนามใน Phase 2 วัดความแม่นจริงก่อนอ้างตัวเลขใด ๆ

- ที่ช้าคือ **ลำดับการโหลดฝั่งหน้าเว็บ**: หน้าจอค้างที่ spinner จนกว่าจะ (1) โหลดสคริปต์ที่บล็อกหน้าครบ, (2) `liff.init` + `getProfile`, (3) `GET /plots`, (4) โหลด Sphere SDK,
  (5) **รอตายตัวอีก 500 ms** แล้วจึงซ่อน spinner → รายการ "แปลงของฉัน" ต้องรอแผนที่ทั้งที่ยังไม่ได้ใช้
- **Rate limit ทำให้ดูเหมือนแอปค้าง:** จำกัด 10 คำขอ/นาที/IP **รวมไฟล์ static** ผมโดน 429 หลังยิงไปแค่ประมาณ 12 ครั้ง
  ถ้าจัดอบรมเจ้าหน้าที่ที่ใช้ Wi-Fi เดียวกัน (IP เดียวกัน) หรือมือถือที่ใช้ CGNAT แอปจะโหลดไม่ขึ้น → **ต้องแก้ก่อนขยายผู้ใช้**
- ยังไม่ได้วัดในแอป LINE บน iOS/Android จริง → Phase 1 จะใส่ตัววัดเวลาฝั่ง client (ส่งกลับมาที่ server) เพื่อเทียบก่อน/หลัง

## 5. ความเสี่ยงและหนี้ทางเทคนิค (เรียงตามความรุนแรง)

**วิกฤต**
1. Admin key หลุดใน repo public (ดูด้านบน)
2. ไม่มี auth ผู้ใช้ / ไม่มีการตรวจสิทธิ์ความเป็นเจ้าของ (ดูด้านบน)
3. Auth แบบ fail-open: ถ้าไม่ได้ตั้ง `ADMIN_API_KEY` ระบบปล่อยผ่าน `/admin/*` ทั้งหมด และถ้าไม่ได้ตั้ง `LINE_CHANNEL_SECRET` ระบบข้ามการตรวจลายเซ็น webhook
4. LIFF ใช้บัญชีร่วม `"test-user"` เมื่อ `liff.init` ล้มเหลว · ไม่ลบ `code`/`state` ออกจาก URL · CORS เปิด `*`

**สูง**
5. Rate limit และ cache เก็บในแรมของโปรเซสเดียว: หายเมื่อ restart และใช้ไม่ได้ถ้ามีหลาย instance · cache ไม่ได้ใช้ polygon เป็น key (แปลงต่างรูปร่างที่จุดกลางใกล้กันจะได้ผลเดียวกัน)
6. CI ไม่เคยรัน → push `master` แล้ว deploy ขึ้น production เลยโดยไม่มี test
7. `main.py` เรียก `load_dotenv()` ทำให้ test ในเครื่องที่มี `backend/.env` ตัวจริงมีโอกาสเรียกบริการจริง
8. Migration รันมือ ไม่มีบันทึกเวอร์ชัน ไม่มีแผน backup
9. ตัวเลขและคำกล่าวอ้างที่ยังไม่ได้ทดสอบ (ข้อ 2.4) + ปุ๋ย/ผลผลิตที่เป็นสูตรของทุเรียน
10. **PDPA:** เก็บ LINE userId, ชื่อโปรไฟล์ และพิกัดแปลง โดยไม่มีหน้าขอความยินยอมหรือนโยบายความเป็นส่วนตัว
11. **ไลเซนส์ Earth Engine:** การใช้เชิงพาณิชย์ต้องมีสิทธิ์แบบ commercial · ต้องตรวจว่า Cloud project ปัจจุบันลงทะเบียนเป็นประเภทไหน ก่อนไปคุย B2G
12. **โควตา LINE OA:** สรุปประจำวันเปิดเป็นค่าเริ่มต้นสำหรับทุกคน (`migrate_v11`) ส่งการ์ดและรูปทุกแปลงทุกเช้า → จำนวนข้อความโตตาม ผู้ใช้ × วัน ต้องเช็กแพลน OA ปัจจุบันก่อนชวนเครือข่าย

**กลาง**
13. LIFF เป็นไฟล์เดียว 2,262 บรรทัด จะเพิ่มบทบาทผู้ใช้หรือหน้าใหม่ได้ยาก
14. Daily scan เรียก GEE ทุกแปลงทุกวัน ค่าใช้จ่าย/โควตาจะโตตามจำนวนแปลง
15. `computeFlowGraph` ฝั่ง JS เป็น O(n²) (ถ้ามี 1,600 จุดคือราว 2.5 ล้านรอบ) อาจหน่วงบนมือถือรุ่นเก่า
16. Hardcode LINE userId จริงไว้ใน `main.py` (endpoint seed) และจุดเริ่มแผนที่ยังอยู่ที่จันทบุรี

## 6. แผนแต่ละ Phase (ปรับให้ตรงกับโค้ดจริง)

ขนาดงานประเมินเป็น "วันทำงาน" โดยประมาณ (S ≤ 1, M 2–4, L 5+)

### Phase 1a — ปิดช่องโหว่ (ใหม่ แทรกก่อน Phase 1) · ~4 วัน · branch `feat/v2-phase1a-security`
- [ผู้ใช้] เปลี่ยน `ADMIN_API_KEY` · [ผม] เอา key ออกจาก `render.yaml`, ให้ admin auth เป็น fail-closed
- LIFF ส่ง ID token → server ตรวจกับ LINE (`/oauth2/v2.1/verify`) → server ใช้ userId จาก token เท่านั้น (ไม่รับจาก URL/body)
- ตรวจความเป็นเจ้าของในทุก endpoint ของแปลง, ใส่ auth ให้ `/iot/reading` (ใช้ key ต่อเซนเซอร์), `/analyze/grid`, `/analyze/preview`, `/weather-alert/preview`
- `history.replaceState` ลบ `code`/`state`, ตัดบัญชีร่วม `test-user` ออก, จำกัด CORS
- Rate limit: ไม่นับไฟล์ static และนับต่อผู้ใช้ (จาก token) แทน IP
- แก้ CI ให้รัน test บน `master` (ไม่ deploy) + test สำหรับการตรวจสิทธิ์
- **พฤติกรรมที่จะเปลี่ยน:** ลิงก์ API เดิมที่ไม่มี token จะใช้ไม่ได้, เปิด LIFF นอก LINE ต้อง login (ตอนนี้ก็บังคับอยู่แล้ว), ส่วน webhook/การ์ด LINE ไม่กระทบ

### Phase 1b — ความเร็ว · ~2 วัน
ทางเลือก (ดูคำถามข้อ 2):
| | ทำอะไร | ข้อดี | ข้อเสีย | ค่าใช้จ่ายเพิ่ม |
|---|---|---|---|---|
| **A (แนะนำ)** | อยู่ Render starter เหมือนเดิม + ปรับลำดับโหลด: defer Chart.js, ไม่โหลด Leaflet ใน production, แสดงรายการแปลงจาก cache ใน localStorage ทันทีแล้วค่อยอัปเดต, โหลดแผนที่หลังแสดงรายการแปลง, ตัด sleep 500 ms, ใส่ cache-control | ไม่ต้องย้ายระบบ ไม่ต้องแก้ LINE Developers | ไฟล์ static ยังมาจาก Render (ซึ่งเร็วอยู่แล้ว) | 0 |
| B | A + ย้าย static ไป Cloudflare Pages | มี CDN, หน้าเว็บยังเปิดได้แม้ API ล่ม | ต้องเปลี่ยน endpoint URL ของ LIFF ใน LINE Developers + ตั้ง CORS | 0 (แพลนฟรี) |
| C | ลด Render กลับเป็น free + B + cache UI | ประหยัดค่า Render | cold start ของ API กลับมา (หลายสิบวินาที) ทำให้การวิเคราะห์ช้ามาก | ติดลบ (ประหยัด) |

### Phase 1c — ชนิดพืช + ประเภทสวน · ~3 วัน
- `crops` เป็นไฟล์ JSON ใน repo (`backend/config/crops.json`) ค่าทางการเกษตรเว้นว่าง `null` · เพิ่มตาราง `plot_crops` + คอลัมน์ `plots.plot_type` (flat / raised_bed / vegetable_bed)
  เป็นการ **เพิ่ม** schema อย่างเดียว ไม่แก้ของเดิม (`migrate_v12.sql` + rollback script) — ต้องรอผู้ใช้อนุมัติ
- UI เลือกพืชได้หลายชนิด + เลือกประเภทสวน ตอนสร้าง/แก้ไขแปลง (ตอนนี้ยังแก้ไขแปลงไม่ได้ ต้องเพิ่ม endpoint `PATCH /plots/{id}`)
- ซ่อนปุ๋ย/ผลผลิตแบบทุเรียนสำหรับพืชอื่น (หรือซ่อนทั้งหมด ดูคำถามข้อ 8)

### Phase 1d — ระบบคำแนะนำ · ~7 วัน
- ตาราง `recommendation_rules` + `recommendation_rule_history` · rule engine `crop × problem × severity → rules` ปรับระดับความรุนแรงตาม `waterlogging_sensitivity`
- ประเภทปัญหาจับคู่กับข้อมูลที่มีอยู่: น้ำขัง (status waterlogged/wet), จุดน้ำรวม (in-degree ≥ 2), แห้งเกิน (dry/drought), ความชื้นในแปลงต่างกันมาก (ช่วง swab_index ในแปลง), ทางน้ำไหลผ่านแนวปลูก (**ข้ามสำหรับสวนยกร่อง/พื้นราบ** เพราะไม่มีข้อมูลรองรับ)
- สวนผสม: รวมคำแนะนำของทุกพืช ตัดข้อที่ซ้ำ และใช้ความรุนแรงตามพืชที่อ่อนไหวที่สุด
- แตะจุดบนแผนที่ → แสดงปัญหา + เหตุผล + วิธีแก้ + ป้าย "ร่าง รอผู้เชี่ยวชาญตรวจ" / "ตรวจแล้วโดย…"
- หน้า admin ใน dashboard: แก้ไข/อนุมัติ/ดูประวัติ
- ร่างกฎตั้งต้น (draft ทั้งหมด) จากข้อความเดิม + export เป็น Excel ให้ส่งเกษตรจังหวัดตรวจ
- unit test: พืชที่ไม่มีกฎ, สวนผสม, ไม่พบปัญหา, แปลงจุดเดียว, ประเภทสวนยกร่อง

### Phase 1e — ประโยคสรุป + คำอธิบายสี · ~2 วัน
- template ที่เติมจากข้อมูลจริง (จำนวนจุดตามประเภทปัญหา + ทิศในแปลงจาก `position_desc` ที่มีอยู่แล้ว) แสดงทั้งใน LIFF และการ์ด LINE
- legend "สีเทียบกันเองในแปลงนี้ ไม่ใช่ระดับความแห้ง/เปียกจริง" ติดกับแผนที่ทุกครั้ง
- สวนยกร่อง: ข้อความระวังข้อจำกัด + ไม่แสดงลูกศรและวงม่วง

### Phase 1f — แชร์รายงาน · ~3 วัน
- สร้างรูปสรุปฝั่ง server ด้วย Pillow (มีอยู่แล้วใน `map_image.py` ไม่ต้องเพิ่ม dependency) + PDF (Pillow บันทึก PDF ได้)
- `liff.shareTargetPicker` — **ต้องเปิดใช้ในหน้าตั้งค่า LIFF ของ LINE Developers ก่อน**

### Phase 1g — พื้นฐานอื่น · ~2 วัน
- `POST /client-errors` เก็บ error จาก LIFF · seed แปลงตัวอย่างราชบุรี 8 แปลง หลายพืช · อัปเดต README/docs

**รวม Phase 1a–1g ≈ 23 วันทำงาน**

### Phase 2 — เครือข่ายเกษตรจังหวัด · ~30 วัน
- บทบาท `farmer/officer/admin` + `area_scope` ใช้รหัสตำบล/อำเภอ (ต้องมีชั้นข้อมูลขอบเขตการปกครอง) · ระบบรหัสเชิญ
- รูปถ่าย: Supabase Storage, บีบอัดฝั่ง client, คิวใน IndexedDB, อ่าน EXIF ฝั่ง client แล้วลบ EXIF ก่อนเก็บ (อาจต้องเพิ่มไลบรารีเล็ก ๆ จะถามก่อน)
- `field_validations`, dashboard จังหวัด + export, `events`, `audit_logs`, PDPA + `docs/data-governance.md`
- **ข้อควรพิจารณา:** ถึงตอนนี้ LIFF ไฟล์เดียวจะดูแลยาก อาจต้องแยกไฟล์หรือเพิ่ม build step (Vite) → จะเสนอให้ตัดสินใจตอนเริ่ม Phase 2

### Phase 3 — แจ้งเตือน + ติดตามระยะยาว · ~10 วัน
- ระบบแจ้งเตือนฝนมีอยู่แล้ว (`weather_alert.py`, `rain_alert_job`) ให้ปรับเป็นระดับจุดเสี่ยงและชนิดพืช + ระบบกันส่งซ้ำ + ประเมินโควตา/ค่าใช้จ่าย OA ก่อนเปิดใช้
- ระดับน้ำ/ความเค็ม: สำรวจ API ของหน่วยงานรัฐ แล้วรายงานก่อนลงมือ

### Phase 4a — จำแนกพืช · ~30 วัน + เวลาเก็บข้อมูล
- ตรวจไลเซนส์ (EE commercial + Satellite Embedding) และปีล่าสุดที่มีในแคตตาล็อกก่อนเริ่ม
- **ตอนนี้ยังไม่มี label เลย** → ต้องรอข้อมูลจาก Phase 2 (ผู้ใช้ยืนยันพืช + รูป + เจ้าหน้าที่ยืนยัน) และ/หรือทะเบียนเกษตรกร งานจริงจึงเริ่มได้หลัง Phase 2 ใช้งานไปสักระยะ
