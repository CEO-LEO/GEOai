## 0. บทบาทและเป้าหมาย

คุณคือ senior full-stack engineer + geospatial/ML engineer ที่ร่วมพัฒนา **IAM ROOT (ตรวจต้นไม้)**
หน้าที่ของคุณคืออัปเกรดแอปจากต้นแบบ (prototype) ให้เป็นเวอร์ชันที่ **ใช้งานจริงกับเครือข่ายเกษตรจังหวัด** ได้
และพร้อมสำหรับการคุยโครงการ **B2G กับเกษตรจังหวัดราชบุรี**

**เป้าหมายของ v2 (เรียงตามความสำคัญ):**
1. ไม่ใช่แค่บอกว่า "เกิดอะไรขึ้นในแปลง" แต่ต้องบอกว่า **"ควรแก้อย่างไร"**
2. รองรับ **พืชหลายชนิด** (ไม่ใช่แค่ทุเรียน) ทั้งไม้ผลและผัก เน้นพืชสวนภาคกลางและภาคตะวันออก
3. รองรับ **เครือข่ายผู้ใช้** (เจ้าหน้าที่เกษตร + เกษตรกร) พร้อมแดชบอร์ดระดับจังหวัด
4. วางรากฐาน **จำแนกชนิดพืชจากภาพถ่ายดาวเทียม**

**ตัวชี้วัดความสำเร็จ:**
- เปิดแอปใน LINE แล้วเห็นหน้าแรกพร้อมใช้ภายในไม่กี่วินาที (ไม่ติด cold start นาน)
- เกษตรกรที่ไม่ถนัดเทคโนโลยีอ่านผลแล้วเข้าใจว่าต้องทำอะไรต่อ โดยไม่ต้องมีคนอธิบาย
- เจ้าหน้าที่เกษตรจังหวัดดูภาพรวมแปลงในพื้นที่รับผิดชอบได้
- มีตัวเลขการใช้งานจริงไว้ใช้เป็นหลักฐานตอนเสนอ B2G

## 1. บริบทโปรเจกต์

### 1.1 สถานะปัจจุบัน
- เว็บแอป **LINE LIFF** deploy บน **Render** (`https://iamroot.onrender.com/liff/`)
- ฟีเจอร์ที่มีอยู่:
  - "แปลงของฉัน" + เพิ่มแปลงใหม่
  - ระบุแปลง 2 แบบ: จิ้มจุดเดียว หรือ "วาดขอบเขต" เป็น polygon (อย่างน้อย 3 จุด)
  - ระบบเตือนถ้าวาดกว้างเกินสวนจริง
  - ตัวเลือกเพิ่มเติม: ค้นหาพิกัด, ตำแหน่งของฉัน, ตั้งชื่อแปลง
  - "ตรวจสอบแปลงนี้" → แสดงจุดแห้งสุด (แดง) / ปานกลาง (เขียว) / แฉะสุด (น้ำเงิน)
    **เป็นสีเทียบกันเองภายในแปลง**, ลูกศรทิศทางน้ำไหล, วงม่วง = จุดน้ำรวมมาก, แตะจุดดูรายละเอียด
  - "จุดน้ำขังในแปลง" และ "ประวัติการวิเคราะห์"

### 1.2 ฟีดแบ็กจากเกษตรจังหวัดราชบุรี (ผู้ใช้นำร่อง)
1. ชอบระบบ และสนใจใช้จริง
2. อยากให้บอกด้วยว่า **แก้อย่างไร** เมื่อบอกว่าเกิดอะไรขึ้น
   → ฟังก์ชันคำแนะนำนี้ **เคยมีและถูกตัดออกไป** ให้ค้น git history (`git log -S`, `git log --all -- <path>`)
   หาโค้ดเดิม แล้วประเมินว่าควรนำกลับมาใช้หรือเขียนใหม่ และพยายามหาเหตุผลที่ถูกตัด (commit message) มารายงาน
3. เจ้าหน้าที่ถ่ายรูปลงพื้นที่เยอะอยู่แล้ว และจะชวน **เครือข่าย** เข้ามาใช้
4. รอบถัดไปต้องเพิ่ม **พืชผักและผลไม้ที่ไม่ใช่ทุเรียน**
5. ถ้าผ่าน → ทำ **B2G** กับเกษตรจังหวัดราชบุรี เพื่อของบประมาณพัฒนาต่อ

### 1.3 กลุ่มผู้ใช้
| ผู้ใช้ | ลักษณะ | ต้องการ |
|---|---|---|
| เกษตรกร | หลายคนอายุมาก ใช้มือถือผ่าน LINE เป็นหลัก สัญญาณในสวนอาจไม่ดี | ผลที่เข้าใจง่าย + บอกว่าต้องทำอะไร |
| เจ้าหน้าที่เกษตร | ลงพื้นที่ ถ่ายรูปเยอะ ดูแลเกษตรกรหลายราย | บันทึกข้อมูลเร็ว ดูหลายแปลง ส่งรายงานได้ |
| ผู้บริหาร/เกษตรจังหวัด | ตัดสินใจเชิงนโยบาย | ภาพรวมระดับอำเภอ/จังหวัด ตัวเลขสรุป |

### 1.4 บริบทพื้นที่ที่ต้องคำนึง
- **ภาคกลาง:** สวนส่วนใหญ่เป็นแบบ **ยกร่องสวน** (คันดินสลับร่องน้ำ) พื้นที่ราบมาก ความสูงต่างกันน้อย
  มีความเสี่ยงน้ำท่วมจากแม่น้ำ และ **น้ำเค็มรุก** ในหน้าแล้ง
- **ภาคตะวันออก:** มี **สวนผสม** (หลายพืชในแปลงเดียว) เยอะ
- หน้าฝนเมฆมาก → ภาพดาวเทียมแบบออปติคัลใช้ไม่ได้หลายเดือน

## 2. กติกาการทำงาน (ต้องทำตามทุกข้อ)

### 2.1 ขั้นตอน
- **เริ่มด้วย Phase 0 เสมอ** สำรวจ → รายงาน → เสนอแผน → **รอผมอนุมัติ** ก่อนแก้โค้ด
- ใช้ plan mode และ task list ติดตามงาน
- ทำทีละ Phase แยก branch ต่อ Phase (`feat/v2-phase1-...`) commit ย่อยและสื่อความหมาย
- **ห้ามทำให้ฟีเจอร์เดิมพัง** ถ้าต้องเปลี่ยนพฤติกรรมเดิม ให้แจ้งก่อน
- อะไรที่ไม่แน่ใจ **ให้ถาม อย่าเดา** และรวมคำถามเป็นชุดเดียว ไม่ถามทีละข้อ

### 2.2 ห้ามทำโดยไม่ถาม
- migrate / ลบ / เปลี่ยน schema ของข้อมูลที่มีอยู่ (ต้องมีแผน backup + rollback)
- เปลี่ยนผู้ให้บริการ hosting, ฐานข้อมูล หรือบริการที่มีค่าใช้จ่าย
- เปลี่ยน LIFF ID, channel, หรือการตั้งค่าใน LINE Developers
- เพิ่ม dependency ขนาดใหญ่

### 2.3 ความปลอดภัย
- secrets / API keys / tokens อยู่ใน env เท่านั้น ห้าม commit ห้าม log
- **ตรวจ LINE ID token ฝั่ง server** (verify กับ LINE API) ห้ามเชื่อ `userId` ที่ client ส่งมาตรง ๆ
- หลัง `liff.init()` ให้ลบ `code` / `state` ออกจาก URL ด้วย `history.replaceState`
  (ป้องกันผู้ใช้คัดลอกลิงก์ที่มี auth code ไปแชร์)
- ตรวจสิทธิ์ตามบทบาทที่ **server ทุก endpoint**
- จำกัดขนาด/ชนิดไฟล์อัปโหลด, rate limit endpoint สำคัญ
- ลบ EXIF ที่ไม่จำเป็นออกจากรูปที่เก็บ (เก็บเฉพาะพิกัดและเวลาไว้ในฐานข้อมูลแยก)

### 2.4 UX สำหรับเกษตรกร
- UI ภาษาไทยทั้งหมด ใช้คำง่าย หลีกเลี่ยงศัพท์เทคนิค (ไม่ใช้คำว่า DEM, NDVI, polygon บนหน้าจอผู้ใช้)
- mobile-first ภายใน LINE, ตัวอักษรใหญ่ ปุ่มกดง่าย (อย่างน้อย 44px) มีไอคอนประกอบ
- ทุกการรอต้องมีสถานะ (skeleton / ข้อความว่ากำลังทำอะไร) ห้ามค้างที่ "กำลังโหลด..." เฉย ๆ
- รองรับสัญญาณอ่อน: งานอัปโหลดรูปต้อง retry ได้และไม่ทำข้อมูลหาย
- **ห้ามแสดงตัวเลขความแม่นยำหรือคำกล่าวอ้างที่ยังไม่ได้ทดสอบจริง**

### 2.5 คุณภาพโค้ด
- เขียน test สำหรับ logic สำคัญ (rule engine คำแนะนำ, การตรวจสิทธิ์, API หลัก)
- มี seed data: แปลงตัวอย่างในราชบุรี 5–10 แปลง หลายชนิดพืช สำหรับทดสอบ
- มี error logging ฝั่ง server และ client (ข้อผิดพลาดใน LIFF ต้องส่งกลับมาดูได้)
- เขียนเอกสารใน `docs/` และอัปเดต README

## 3. Phase 0 — สำรวจและวางแผน (ห้ามแก้โค้ดใน Phase นี้)

ส่งรายงานให้ผมเป็นข้อ ๆ:
1. **สถาปัตยกรรมปัจจุบัน:** stack frontend/backend, โครงสร้างโฟลเดอร์, ฐานข้อมูลและ schema, วิธี deploy, env ที่ใช้
2. **การวิเคราะห์แปลงทำงานอย่างไร:** ใช้ข้อมูลจากแหล่งไหน (DEM? ดาวเทียม? API?) ความละเอียดเท่าไร คำนวณทิศทางน้ำ/จุดน้ำขังอย่างไร
   และ **ประเมินว่าใช้ได้กับสวนยกร่องภาคกลางที่พื้นที่ราบมากหรือไม่**
3. **ผลค้น git history** เรื่องฟังก์ชันคำแนะนำที่ถูกตัด
4. **ปัญหาความเร็ว:** วัดเวลาโหลดจริง ระบุสาเหตุ (cold start, bundle ใหญ่, API ช้า, แผนที่โหลดช้า)
5. **ความเสี่ยงและหนี้ทางเทคนิค** ที่ต้องแก้ก่อนขยายผู้ใช้ (ความปลอดภัย, การตรวจ token, การ scale)
6. **แผนแต่ละ Phase** ปรับจาก spec นี้ให้เข้ากับโค้ดจริง พร้อมประเมินขนาดงาน
7. **คำถามที่ต้องให้ผมตอบ** (ดูหัวข้อ 9 ประกอบ)
8. สร้างไฟล์ **`CLAUDE.md`** ที่ root สรุปบริบทโปรเจกต์ stack คำสั่ง build/test/deploy และกติกาจากหัวข้อ 2
   เพื่อให้ session ถัดไปเริ่มงานได้ทันที

## 4. Phase 1 — พื้นฐาน + ระบบคำแนะนำ (สำคัญที่สุด)

### 4.1 ความเร็วในการโหลด
- เสนอทางเลือก 2–3 แบบพร้อมข้อดี/ข้อเสีย/ค่าใช้จ่าย ให้ผมเลือก เช่น
  - แยก frontend ไป static hosting (Vercel / Netlify / Cloudflare Pages) เหลือ Render เป็น API
  - อัปเกรดแพลน Render ให้ไม่หลับ
  - แสดง UI ได้ทันทีจาก cache ขณะรอ API ตื่น
- ลดขนาด bundle, lazy load แผนที่, cache ผลวิเคราะห์ของแปลงที่เคยตรวจแล้ว

### 4.2 สรุปผลเป็นภาษาคน
- ทุกผลวิเคราะห์มี **ประโยคสรุป 1–2 บรรทัดด้านบน** เช่น
  "แปลงนี้ระบายน้ำค่อนข้างดี มีจุดเสี่ยงน้ำขัง 2 จุดทางทิศใต้"
- อธิบายให้ชัดว่า **สีเทียบกันเองภายในแปลง** ไม่ใช่ค่าสัมบูรณ์ ป้องกันการเข้าใจผิดว่าสีแดง = แห้งวิกฤต
- ให้สรุปผลจาก template + ข้อมูลจริง ไม่ใช้ AI แต่งข้อความ

### 4.3 ชนิดพืช
- เลือกชนิดพืชตอนสร้าง/แก้ไขแปลง (เลือกได้หลายชนิดสำหรับสวนผสม)
- รายการพืช **config ได้** (ไฟล์ JSON หรือตาราง DB) ไม่ hardcode
- รายการเริ่มต้น (อาจเปลี่ยนตามที่เกษตรจังหวัดเลือก):
  - **ไม้ผล:** ทุเรียน, ส้มโอ, มะพร้าวน้ำหอม, มะม่วง, ฝรั่ง, ชมพู่, มะนาว, กล้วย, มังคุด, เงาะ, ลำไย, องุ่น
  - **ผัก:** กลุ่มผักทั่วไป (logic แยก เพราะรอบปลูกสั้น และมักปลูกแบบยกแปลง)
  - **อื่น ๆ:** ระบุเอง
- ตัวอย่าง schema (ค่าทางการเกษตรให้เว้นว่างไว้ให้ผู้เชี่ยวชาญกรอก **ห้ามเดาตัวเลข**):

```json
{
  "id": "durian",
  "name_th": "ทุเรียน",
  "group": "fruit_tree",
  "perennial": true,
  "waterlogging_sensitivity": "high",
  "thresholds": {
    "waterlogging_risk": null,
    "dryness_risk": null
  },
  "notes_th": "",
  "reviewed_by": null,
  "reviewed_at": null
}
```

- ใช้ `waterlogging_sensitivity` (high / medium / low) ปรับระดับความรุนแรงของคำเตือนตามพืช

### 4.4 ระบบคำแนะนำ "แก้อย่างไร"
- โครงสร้าง: **ตารางกฎ พืช × ปัญหา × ระดับความรุนแรง → คำแนะนำ**
- ประเภทปัญหาเริ่มต้น: น้ำขัง, จุดน้ำรวม, แห้งเกิน, ทางน้ำไหลผ่านแนวปลูก, ความต่างความชื้นในแปลงสูง
- ตัวอย่าง schema:

```json
{
  "id": "durian-waterlogging-high",
  "crop_id": "durian",
  "problem": "waterlogging",
  "severity": "high",
  "title_th": "จุดเสี่ยงน้ำขัง",
  "actions_th": [
    "ขุดร่องระบายน้ำออกจากจุดนี้",
    "ยกโคกก่อนปลูกต้นใหม่",
    "หลีกเลี่ยงการปลูกต้นใหม่ตรงจุดนี้"
  ],
  "why_th": "",
  "status": "draft",
  "reviewed_by": null,
  "source": ""
}
```

- `status`: `draft` (รอตรวจ) / `reviewed` (ตรวจแล้วโดยเกษตรจังหวัด) — **แสดงสถานะให้ผู้ใช้เห็น**
- ข้อความคำแนะนำต้องมาจากตารางที่คนเขียน/ตรวจเท่านั้น **ห้ามให้ AI สร้างคำแนะนำแบบ real-time**
- คำแนะนำผูกกับจุดในแผนที่: แตะจุด → เห็นปัญหา + เหตุผล + วิธีแก้
- ทำ **หน้า admin** ให้ผู้เชี่ยวชาญแก้ไข/อนุมัติคำแนะนำได้โดยไม่ต้องแก้โค้ด (เก็บประวัติการแก้)
- ร่างคำแนะนำเบื้องต้นได้ แต่ต้องตั้งเป็น `draft` ทั้งหมด และรวบรวมเป็นไฟล์ให้ผมส่งเกษตรจังหวัดตรวจ
- เขียน unit test ครอบคลุม rule engine (พืชไม่มีกฎ, สวนผสมหลายพืช, ไม่พบปัญหา ฯลฯ)

### 4.5 รองรับสวนยกร่อง (ภาคกลาง)
- จากผล Phase 0 ถ้าข้อมูลความสูงละเอียดไม่พอ ให้:
  - เพิ่มตัวเลือก "ประเภทสวน": แปลงเรียบ / ยกร่อง / ยกแปลงผัก
  - สำหรับสวนยกร่อง ปรับข้อความผลวิเคราะห์ให้ระมัดระวัง และบอกข้อจำกัดตรง ๆ
  - เสนอแนวทางปรับปรุงการวิเคราะห์ให้ผมพิจารณา (ไม่ต้องลงมือใน Phase นี้)

### 4.6 รายงานส่งต่อได้
- ปุ่ม "แชร์รายงาน" สร้างรูปสรุป (แผนที่ + สรุปผล + คำแนะนำ) แชร์ใน LINE ได้ด้วย `liff.shareTargetPicker`
  และดาวน์โหลดเป็น PDF ได้

**Definition of Done Phase 1:**
- [ ] เวลาโหลดดีขึ้นอย่างวัดได้ (รายงานก่อน/หลัง)
- [ ] ทุกผลวิเคราะห์มีประโยคสรุปและคำอธิบายสี
- [ ] เลือกพืชได้ รวมถึงสวนผสม
- [ ] คำแนะนำแสดงต่อจุด พร้อมสถานะ draft/reviewed
- [ ] หน้า admin แก้คำแนะนำได้
- [ ] แชร์รายงานใน LINE ได้
- [ ] test ผ่าน และทดสอบใน LINE จริงทั้ง iOS และ Android

## 5. Phase 2 — รองรับเครือข่ายเกษตรจังหวัด

### 5.1 บทบาทผู้ใช้
- `farmer`: เห็น/แก้เฉพาะแปลงตัวเอง
- `officer`: เห็นแปลงในพื้นที่รับผิดชอบ (ระดับตำบล/อำเภอ), สร้างแปลงแทนเกษตรกรได้, แนบรูป, ยืนยันข้อมูล
- `admin`: จัดการผู้ใช้ บทบาท พื้นที่ รายการพืช และคำแนะนำ
- ระบบเชิญเจ้าหน้าที่ด้วยลิงก์/รหัสเชิญ (ไม่ต้องสมัครเอง)

### 5.2 รูปถ่ายภาคสนาม
- แนบรูปเข้ากับแปลง หรือจุดในแผนที่ อ่านพิกัด GPS + เวลาจาก EXIF ถ้ามี
- บีบอัดรูปฝั่ง client ก่อนอัปโหลด, คิวอัปโหลดเมื่อสัญญาณกลับมา
- แท็กรูปได้: ชนิดพืช, อาการที่เห็น (น้ำขัง, ใบเหลือง, โคนเน่า ฯลฯ)

### 5.3 การยืนยันภาคสนาม (ground truth)
- ที่แต่ละจุดที่ระบบวิเคราะห์ ให้ผู้ใช้ตอบได้: "จริง / ไม่จริง / ไม่แน่ใจ"
- เก็บข้อมูลนี้แยกตาราง ใช้วัดความแม่นของการวิเคราะห์ และเป็น label สำหรับ Phase 4

### 5.4 แดชบอร์ดระดับจังหวัด
- จำนวนแปลง พื้นที่รวม จำนวนเกษตรกร แยกตามอำเภอ/ตำบล และชนิดพืช
- แผนที่รวมจุดเสี่ยง (ระดับภาพรวม ไม่เปิดเผยข้อมูลส่วนบุคคลเกินสิทธิ์)
- export CSV / Excel สำหรับหน่วยงาน

### 5.5 สถิติการใช้งาน (สำหรับ B2G)
- เก็บ event: เปิดแอป, สร้างแปลง, วิเคราะห์, ดูคำแนะนำ, แชร์รายงาน, อัปโหลดรูป
- หน้าสรุปสถิติสำหรับ admin: ผู้ใช้ใหม่/ผู้ใช้ประจำ รายสัปดาห์, จำนวนแปลง, จำนวนครั้งวิเคราะห์

### 5.6 PDPA
- หน้าขอความยินยอมครั้งแรก (เก็บพิกัดแปลง, รูปถ่าย, ข้อมูลโปรไฟล์ LINE)
- นโยบายความเป็นส่วนตัวภาษาไทย, ผู้ใช้ขอดู/ลบข้อมูลตัวเองได้
- audit log ว่าใครเข้าดู/แก้ข้อมูลแปลงของใคร
- ร่างเอกสาร `docs/data-governance.md` สรุปการเก็บและใช้ข้อมูล ใช้ประกอบการคุยกับหน่วยงานรัฐ

**Definition of Done Phase 2:**
- [ ] 3 บทบาททำงานถูกต้อง ตรวจสิทธิ์ฝั่ง server และมี test
- [ ] อัปโหลดรูปพร้อมพิกัดได้ ทนสัญญาณอ่อน
- [ ] ยืนยันจุดภาคสนามได้
- [ ] แดชบอร์ดจังหวัด + export ได้
- [ ] มีสถิติการใช้งาน
- [ ] มีหน้าขอความยินยอมและนโยบายความเป็นส่วนตัว

## 6. Phase 3 — แจ้งเตือนผ่าน LINE OA + ติดตามระยะยาว

### 6.1 แจ้งเตือนฝน
- ดึงพยากรณ์ฝนตามพิกัดแปลง (เสนอแหล่งข้อมูลพร้อมเงื่อนไขการใช้งาน ให้ผมเลือก)
- ถ้าฝนหนักในแปลงที่มีจุดเสี่ยงน้ำขัง → push message ผ่าน Messaging API
  เช่น "พรุ่งนี้ฝนหนัก แปลง A มีจุดเสี่ยงน้ำขัง 2 จุด แตะดูวิธีเตรียมรับมือ"
- ผู้ใช้ตั้งค่าเปิด/ปิด และระดับความถี่ได้, ป้องกันส่งซ้ำ
- ระวังโควตาข้อความของ LINE OA: คำนวณค่าใช้จ่ายโดยประมาณให้ผมก่อนเปิดใช้

### 6.2 แจ้งเตือนเฉพาะภาคกลาง (ตัวเลือก)
- ระดับน้ำแม่น้ำ / ความเค็มรุก จากข้อมูลหน่วยงานรัฐ ถ้ามี API ที่ใช้ได้ ให้สำรวจและรายงานก่อนทำ

### 6.3 ติดตามระยะยาว
- เทียบผลวิเคราะห์ข้ามช่วงเวลา (เช่น หน้าฝนกับหน้าแล้ง) จากประวัติที่มีอยู่
- **ปักหมุดต้นไม้รายต้น** (ตัวเลือก): บันทึกอาการ รูป วันใส่ปุ๋ย/พ่นยา ต่อต้น

## 7. Phase 4 — จำแนกชนิดพืชจากภาพถ่ายดาวเทียม

**เป้าหมาย:** ระบบเสนอได้ว่าแปลงนี้ "น่าจะปลูกอะไร" เน้นพืชสวนภาคกลางและภาคตะวันออก
นำร่องที่ **จ.ราชบุรี** 4–6 พืชหลักก่อน

### 7.1 สถาปัตยกรรม
- แยกเป็น **service ต่างหาก** (เช่น Python + Google Earth Engine) เรียกผ่าน API จากแอปหลัก
- ประมวลผลแบบ batch / cache ผลต่อแปลง ไม่คำนวณสดทุกครั้งที่เปิด

### 7.2 ข้อมูลนำเข้า (Phase 4a)
- **Satellite embedding สำเร็จรูป:** AlphaEarth Foundations Satellite Embedding ใน Earth Engine
  (64 มิติ ต่อช่อง 10 m รายปี) — ตรวจว่าปีล่าสุดที่มีในแคตตาล็อกคือปีไหน
- **Sentinel-2:** composite รายเดือน + cloud mask, ดัชนีพืชพรรณรายเดือนเพื่อดูรอบการเติบโต (phenology)
- **Sentinel-1 (เรดาร์):** VV/VH ทะลุเมฆได้ สำคัญมากในหน้าฝน
- ⚠️ **ก่อนใช้งานจริง ให้ตรวจเงื่อนไขไลเซนส์ของ Earth Engine และชุดข้อมูล embedding
  สำหรับการใช้เชิงพาณิชย์และงานกับหน่วยงานรัฐ แล้วรายงานผม** (บางชุดข้อมูลฟรีเฉพาะงานไม่ใช่เชิงพาณิชย์)

### 7.3 โมเดล
- **โมเดลเดียวแบบหลายคลาส หรือแบบลำดับขั้น:** เป็นพื้นที่สวนไหม → กลุ่มพืช → ชนิดพืช
- **ห้ามทำโมเดลแยกพืชละตัวแบบ yes/no** เพราะจะได้ผลขัดกันที่จุดเดียวกัน
- เริ่มจากโมเดลเบา (เช่น logistic regression, random forest, gradient boosting บน embedding) ก่อน deep learning
- มีคลาส **"สวนผสม"** และ **"ไม่แน่ใจ"** — ถ้าความมั่นใจต่ำกว่าเกณฑ์ ให้ตอบว่าไม่แน่ใจ ไม่ฝืนทาย
- output: ความน่าจะเป็นของแต่ละพืช (top-3) + ระดับความมั่นใจ
- จัดการข้อมูลไม่สมดุล (บางพืชมีตัวอย่างน้อย)

### 7.4 การประเมินผล
- **แบ่ง train/test แบบเชิงพื้นที่ (spatial split / spatial cross-validation)** ไม่สุ่มแบบพิกเซล
  เพื่อไม่ให้ความแม่นสูงเกินจริงจากแปลงใกล้กัน
- รายงาน accuracy, F1 ต่อพืช, confusion matrix, ผลแยกตามอำเภอ
- ทำสคริปต์ประเมินที่รันซ้ำได้ และเก็บผลแต่ละเวอร์ชันโมเดลไว้เทียบกัน

### 7.5 เรื่องอัพสเกลภาพ (super-resolution)
- **ห้ามใช้ภาพที่ผ่าน super-resolution เป็น input ของการจำแนก** เพราะโมเดลอัพสเกลเดารายละเอียดขึ้นเอง
- ใช้ได้เฉพาะเพื่อแสดงผลให้ดูชัดขึ้น และต้องติดป้ายบนภาพว่า "ภาพปรับความคมชัด ไม่ใช่ภาพจริง"

### 7.6 UI แบบทาย + ยืนยัน
- ตอนสร้างแปลง ระบบเสนอ "แปลงนี้น่าจะเป็น: มะพร้าวน้ำหอม / ส้มโอ / ..." พร้อมระดับความมั่นใจ
- ผู้ใช้กด ใช่ / ไม่ใช่ / เลือกพืชอื่น — ระบบห้ามตัดสินเองทั้งหมด

### 7.7 วงจรข้อมูลฝึก
- ทุกแปลงที่ผู้ใช้ยืนยันชนิดพืช + รูปถ่ายมีพิกัด + การยืนยันจากเจ้าหน้าที่ = label
- ให้น้ำหนักกับ label ที่เจ้าหน้าที่ยืนยันมากกว่า
- pipeline export ชุดข้อมูลและเทรนใหม่เป็นรอบ ๆ, versioning ทั้งข้อมูลและโมเดล
- รองรับนำเข้าข้อมูลแปลงจาก **ทะเบียนเกษตรกร** (ถ้าได้มาผ่านเกษตรจังหวัด) เป็นชุดข้อมูลตั้งต้น

### 7.8 เผื่อต่อยอด (Phase 4b — ออกแบบ interface ไว้ ยังไม่ต้องทำ)
- ภาพความละเอียดสูง **THEOS-2 ของ GISTDA (~0.5 m)** และภาพโดรน
  สำหรับตรวจจับทรงพุ่ม นับต้น และแยกชนิดรายต้น
- ทำ adapter ให้เพิ่มแหล่งภาพใหม่ได้โดยไม่ต้องแก้ส่วนอื่น

**Definition of Done Phase 4a:**
- [ ] service จำแนกพืชทำงานกับแปลงในราชบุรี
- [ ] รายงานผลประเมินแบบ spatial split ต่อพืช
- [ ] UI ทาย + ยืนยัน ทำงานในแอป
- [ ] label จากผู้ใช้ไหลกลับเข้าชุดข้อมูลฝึกได้
- [ ] รายงานเรื่องไลเซนส์ข้อมูล

## 9. คำถามที่ผมจะตอบให้ (ถ้าข้อไหนยังไม่มีคำตอบ ให้ใช้ค่าเริ่มต้นที่ระบุ แล้วแจ้งผม)
1. พืชที่เกษตรจังหวัดอยากให้ทำก่อน → ค่าเริ่มต้น: มะพร้าวน้ำหอม, ฝรั่ง, ชมพู่, องุ่น, ส้มโอ, ทุเรียน
2. งบค่า hosting ต่อเดือน → ค่าเริ่มต้น: เลือกทางที่ฟรีหรือถูกที่สุดที่แก้ cold start ได้
3. จะเก็บเงินผู้ใช้หรือขายให้รัฐ (มีผลกับไลเซนส์ข้อมูล) → ค่าเริ่มต้น: ถือว่าเป็นเชิงพาณิชย์ ต้องตรวจไลเซนส์
4. พื้นที่นำร่อง → ค่าเริ่มต้น: จ.ราชบุรี
5. เกษตรจังหวัดจะช่วยตรวจคำแนะนำหรือไม่ → ค่าเริ่มต้น: ทุกคำแนะนำเป็น draft จนกว่าจะมีผู้ตรวจ
